# Ragent 回归验证台

对一个**已经跑起来的**环境做行为验证：登录、按剧本串行提问、读库看状态、给判定。它不写任何业务数据，
也不删任何东西，跑完的会话留在库里，随时可以再查。

当前只有一个套件 `agent-memory`，验证 ReAct Agent 的三层记忆。

它和 `resources/initializer` 是同一套 CLI：同样的 Java 17、同样不启动 Spring、同样复用
`common/` 下的配置、HTTP 与 JDBC 客户端。区别是初始化器负责**造出确定状态**，回归台负责**验证运行时行为**。

## agent-memory 套件

### 它验证什么

| 层 | 机制 | 剧本怎么验 | 现状 |
| --- | --- | --- | --- |
| 短期 | 工具结果清理（`AgentContextTrimmer`） | t01 植入知识库里查不到的锚点，t02~t07 把上下文撑大到触发清理，t08 要求原样复述锚点 | 已实现，硬断言 |
| 中期 | 安全前缀压缩 + 会话摘要（`AgentContextCompactor`） | t09 问只在 t02 说过一次的工位号；t14 问 t10 更正过的资产编号。两轮都**不许重新检索** | 已实现，硬断言 |
| 长期 | 跨会话用户事实 | t15 另开一条会话直接问工号 | 未实现，答不出记 PENDING |

未实现的层不判死是有意的：**P2 落地后只要把 `MemoryTurnScript.IMPLEMENTED_TIERS` 里加上
`long-term`，同一份剧本自动从 PENDING 转成硬断言**，这套剧本同时也是最后一层的验收用例。

两条中期断言各验一件事，都建立在同一个前提上——**被问的事实只说过一次，之后再没被复述**，
所以它一旦被压缩吃掉，答对就只可能来自摘要：

- **t09（保真）**：工位号 `B3-1207` 只在 t02 出现过，知识库里查不到、问题里也没带。答对说明用户原话
  被摘要 verbatim 带过来了。同轮保留 `forbid-tool`：又调一次 `search_knowledge` 就是 FAIL——那说明摘要
  没把工具结论带过来，模型只能回头重查。
- **t14（取新）**：t01 说资产编号是 `NB-2049`，t10 更正为 `NB-3160`。答旧值即 FAIL——那说明第一代摘要
  里的旧值被逐代抄了下来，「与新记录冲突时以新记录为准」没有真的生效。

关键词式断言只有在这个形态下才站得住。反例是本剧本早先那版 t09（`归还|资产|交接`）：三个词问题里就带着，
模型凭空编一句也能 PASS。

### 两层记忆按水位分工，不是二选一

预算的 **50% 起裁工具结果**（换成占位、不删消息、不调模型），**80% 起才压缩**（真删早期原文、要调一次
模型、有损）。低破坏的手段永远先动手。

**但「多数会话靠裁剪就把水位摁住」实测不成立，上界只有压缩给得了。** 裁剪只改写 `tool_result`，射程等于
它在上下文里的占比，而那是**语料属性不是常量**。08-25 关掉压缩跑满 15 轮，末轮 30575 字符的构成是：

| 块类型 | 字符 | 占比 | 裁剪能动吗 |
| --- | --- | --- | --- |
| `text`（用户话 + 助手回答） | 13823 | 45.2% | ✗ |
| `thinking` | 8039 | 26.3% | ✗ 明令永不清理 |
| `tool_result` | 6851 | 22.4% | ✓ 但 11/26 块已是占位 |
| `tool_use` | 1862 | 6.1% | ✗ |

射程 22.4% 对下限 20%（占**当前总量**，分母还一直涨）——下限顶在射程天花板上，所以裁剪在 t04/t06 各成功
一次之后连续九轮空转，上下文一路涨到预算的 **3.8 倍**。光 `thinking` 一项就比整个可裁剪面还大。

**这条直接决定 `summary-enabled: false` 的性质**：它是摘要模型不可用时的运维出口，但**不是有界的降级**
——关掉之后没有任何东西摁得住水位，一直涨到模型真实窗口报 overflow，而那一轮整个不落库（见下文）。
工具吐大块的语料（一次检索几万字符）裁剪才是主力层，那种形态下这张表会反过来。

代价说在前面：压缩的素材因此可能已经被裁过。占位里带着当时的检索问题，而 `search_knowledge` 返回的
本就是合成后的答案、助手回答里还会复述一遍，所以摘要的 `## 工具与发现` 一节会变薄但不至于空。这是这版
设计明知并接受的取舍，不是 bug。

**「裁剪会把水位摁住、压缩因此永远等不到」这个担心，实测不成立**（8000 预算、白名单原样留着 `search_knowledge`
跑满 15 轮）：压缩照样发生了 4 次，裁剪只成功了 1 次。原因在 `KEEP_RECENT_CYCLES = 2`——十几轮的会话里
每轮只有两三个循环，最近两个一保护，裁剪就够不着「回收量 ≥ 当前总量 20%」那道下限，整层多数轮次空转，
水位照旧涨到压缩门。所以清空 `evictable-tools` 的作用是**让报告只剩压缩这一层、读起来不串**，不是让压缩
得以发生的前提。反过来说，短会话里真正难确定性触发的是**裁剪**，不是压缩。

**两层防的都是跨轮慢涨，单轮 ReAct 内部顶穿上下文不在射程内。** 一轮里的循环全受保护，那时裁剪裁不出
字节来，压缩也只在轮次静默点判。

`context-window-chars` 是**会话上下文工程预算**，不是模型物理上限的字符换算值，所以「预算离标称窗口还差
多少」不能拿来当安全余量算。能用来裁决的只有实测——本机 12 条会话、16 轮、25 次模型调用，读
`t_agent_state.payload->'context'` 里供应商回填的 `usage`，字符数按 `AgentContextChars` 口径在 SQL 侧复算：

| 量 | 实测 |
| --- | --- |
| 单轮上下文增量峰值 | 8,810 字符 |
| 单次 ReAct 循环增量峰值 | 5,794 字符 / 3,667 token |
| 单块 `tool_result` | max 3,271 / p90 2,781 / 均值 725 |
| 单轮模型调用数峰值 | 5 次（上限 `agent.max-iters: 10`） |
| 固定开销（人设 + 工具 schema） | 2,855 token |
| 语料折算 | 约 1.6 字符/token |

按峰值循环 × `max-iters: 10` 外推，单轮上界约 5.8 万字符，远小于生产预算给两道门留出的空间。**这条外推只
对 `search_knowledge` 成立**：`KnowledgeSearchFacade.search()` 返回的是再合成一次的答案（`llmService.chat`），
原始 chunk 根本进不了 Agent 上下文，产出被答案模型自己的输出上限卡着，与 `rag.search.default-top-k` 无关。
**输出不受限的 MCP 工具没有这道界，那条路径是「尚未量化验证的已知风险」**——样本里的 `leave_query` 最大只有
193 字符，但那是这一个工具的观测值，约束不了整个 MCP 工具集。样本量也撑不起 P99：25 次调用、单轮最多 5 次
循环，能报的只有 max。

**真撞上之后不是「下一轮自愈」，是那一轮整个不落库**（逐行核过 `agentscope-core` 2.0.2）：`saveStateToSession`
只挂在成功路径的 `flatMap` 上（`ReActAgent.java:1021`），异常走 `AgentBase.createErrorHandler` 直接
`Mono.error` 重抛、不保存；而 `activateSlotForContext` 在 `stateStore != null` 时**每次调用都从库里重新
加载**并覆盖内存缓存（我们还额外挂了 `evictStateCache`）。所以失败那轮的用户问题、工具结果、助手输出
一个字节都进不了 `agent_state`，下一轮读到的仍是这一轮**开始前**的水位 —— 会话不会因此膨胀，但同一个
问题重问会**同样地再失败一次**，任何水位常量都救不了。（失败轮的消息同样没进 `t_agent_message`，见
`AgentStreamEventBridge:158`，那是已知待修项，不是这次引入的。）

### 前置条件

- JDK 17，`java` 与 `javac` 都在 PATH；
- RagentAI、PostgreSQL 已启动，服务读的是 `bootstrap/src/main/resources/application.yaml`；
- `ragent.engine.type=agent`——`workflow` 档位走的是 RAG 编排管线，根本没有 Agent 记忆；
- **`enterprise-knowledge-base` 模板已经初始化过**。中间 6 轮撑量问题取自该模板，库里没内容就检索
  不到东西，上下文涨不起来，清理永远不触发，整场跑完只会得到一堆 UNCOVERED；
- 账号 `admin/admin` 可登录，在 `regression.properties` 里改。

### 跑一次

在项目根目录执行：

```bash
rm -rf /tmp/ragent-regression-classes && mkdir -p /tmp/ragent-regression-classes

javac -encoding UTF-8 \
  -d /tmp/ragent-regression-classes \
  resources/initializer/common/*.java \
  resources/regression/agent-memory/*.java

java -cp /tmp/ragent-regression-classes \
  com.nageoffer.ai.ragent.initializer.AgentMemoryRegressionMain \
  --suite-dir resources/regression/agent-memory
```

15 轮全是真实模型调用，通常要跑十分钟上下。加 `--verbose` 会顺带打印每轮回答的前 400 字——判断模型
是真记得还是蒙对了关键词，只能靠人看这一段。

看到 `[regression] SUCCESS` 才算通过。任何一条 FAIL 都会以非零状态退出。

改过 `resources/regression/**` 或 `resources/initializer/common/**` 之后，编译这一步必须重跑。

### 怎么读报告

报告有四段：

**逐轮观测**——每轮的回答字数、上下文消息数、工具循环数、≈字符数、tool_result 块数、已清理块数、
摘要消息数、payload 字节。`摘要` 列从 0 变 1 的那一轮就是压缩落点，同一轮的 `消息数` 与 `≈字符`
会同时掉下来——这是压缩唯一的、可自动检出的痕迹。`≈字符` 是在 SQL 侧按 `AgentContextChars` 的口径
复算的，其中 `tool_use` 的入参服务端算的是 `Map.toString()` 长度、这里算 JSON 文本长度，**所以它是
近似值**。要精确数字请看服务端日志的 `上下文裁剪完成` / `上下文裁剪跳过` / `上下文压缩完成`。

**阈值校准**——七个指标。**能回填的只有 `context-window-chars` 一个数**，其余六个比例是编译期常量，
所以这张表读的不是「该调哪个键」，而是「这个数说明什么」：

| 指标 | 这个数说明什么 |
| --- | --- |
| ① tool_result 体量分布 | 单块多大。配合②看：合计够不够当前总量的两成，够不着就是裁剪永远空转的原因 |
| ② 上下文总量峰值 | 峰值离两道门有多远。离得太远就是本次没覆盖到，该动的是预算或撑量轮 |
| ③ 输入 token 峰值 | 供应商回填的权威读数。**不要拿它去除②算字符/token**：②只算会话上下文，③含人设与工具 schema（实测固定开销 2855 token），两个峰值还可能来自不同次调用。折算比例见下方实测表，那是**填预算时**的工作负载换算，不是运行期不变量 |
| ④ 命中缓存峰值 | 两层都会改写前缀让缓存失效。之后这个数掉下来，说明回收的量不值那次缓存击穿 |
| ⑤ 工具循环 / thinking 块 | 保两个循环够不够用（常量 2）；thinking 块数量是它永远不被清理的证据 |
| ⑥ 压缩落点 | 保留段（预算的 20%）与峰值的关系。压缩「换不掉过半字节就不动」，越过压缩门时素材天然占四分之三，卡住只会是尾段太肥把切点顶到了头部 |
| ⑦ 摘要产物 | 末轮摘要消息条数与派生出的正文上限（预算 10%，夹进 1500~6000）。摘要写得对不对只能人看，用 `AgentMemoryProbeMain` 打开末轮状态，它会把末代摘要正文整段印出来 |

**摘要长度随用户轮数单调涨，这是设计的直接后果不是漂移**：`## 用户诉求` 一节逐条 verbatim 且明令不参与
再压缩，所以每多一个用户轮它就多一行。实测四代 638 → 778 → 1106 → 1285 字符，本机语料约 70 字符/用户轮。
上限是唯一的界，顶到之后 `validate` 在最后一个完整 `\n## ` 边界截断——掉的是**尾部**小节（`## 下一步` 先走），
排第一的 `## 用户诉求` 最安全，降级方向是对的。按这个斜率，调试预算的 1500 上限约在第 5~6 代开始咬，
生产预算的 6000 够到八十轮上下；**换语料要重算这个斜率，别照抄 70**。

上下文里只留得住最后一代摘要，前几代被覆盖后就没了。要看某一代到底丢了什么，查审计表：

```sql
SELECT generation, material_msg_count, material_chars, summary_chars,
       context_chars_before, context_chars_after, create_time, summary
FROM t_agent_context_compaction
WHERE conversation_id = '<会话ID>'
ORDER BY generation;
```

这张表是追加型日志，应用侧没有读路径，压缩删掉的原文只在这里留下凭据。

被**裁剪**换成占位的工具结果是另一条路：占位重建时保留了原块的 `id`，而 `t_agent_message.blocks`
里每个 tool 块都带着同源的 `toolCallId`，所以原文能精确回查。先从状态里取 id——
`AgentMemoryProbeMain` 打印的上下文里那条占位所属的 `tool_result` 块，或直接查 `t_agent_state`——
再拿它翻冷日志：

```sql
SELECT m.create_time, b->>'name' AS tool, b->>'result' AS result
FROM t_agent_message m, LATERAL jsonb_array_elements(m.blocks) b
WHERE m.conversation_id = '<会话ID>'
  AND b->>'toolCallId' = '<tool_call_id>';
```

按 `conversation_id` 收窄是必须的：`blocks` 上没有 GIN 索引，不带这个条件就是全表扫。端点不回
`toolCallId` 时该字段为空，此时只能按 `create_time` 顺着时间线找——被压缩删掉的消息也只有这一条路，
它在上下文里连块都不剩了。冷日志本身的单块上限是 `AgentStreamEventBridge.TOOL_RESULT_MAX_CHARS`
（64000 字符），比这更长的结果在冷日志里也是截断的。

**判定**——五种状态：

- `PASS` 通过；
- `FAIL` 回归，退出码非零；
- `PENDING` 该层还没实现，答不出是当前的正确行为；
- `UNEXPECTED` 没实现却命中了，需要人复核是不是走了别的路径蒙对的；
- `UNCOVERED` 本次没跑到这个分支，不算回归，但也不能算验过。

**本次会话**——主会话与新会话的 ID，拿去做单会话排查。

### 让压缩确定性地触发

服务端只有 `context-window-chars` 一个数要配，它是**会话上下文工程预算**而不是模型标称窗口的字符换算值：
人设、工具 schema、本轮输出预留都不走这份账，填数时就该先扣掉。裁剪门是它的 50%、压缩门 80%、压缩后
保留 20%，摘要正文上限同样从它派生（10%，再夹进 1500~6000 之间）。生产值是 120 万字符，压缩门落在
96 万；实测一条十余轮会话不到七千字符，**按生产值跑，两层一次都不会触发**，报告会给两条 UNCOVERED，
t09 与 t14 两条中期判定则会 FAIL。这说明的是「这次没跑到」，不是「代码坏了」——但机制没被验过就是没被
验过。

要确定性地覆盖压缩逻辑，把预算调到实测峰值附近，重启服务再跑一遍：

```yaml
agent:
  memory:
    context-window-chars: 8000  # 压缩门落在 6400，取报告里「上下文总量峰值」的 0.8 倍附近即可
    evictable-tools: [ ]        # 可选：清空后报告里只剩压缩这一层，读起来不串；不清也压得到（见上文实测）
```

改完 **必须重启进程**，配置是 `@ConfigurationProperties` 一次性绑定的。重跑后应当看到（括号里是
2026-08-25 那跑的实测值，白名单当时没清、两层都在）：

- 校准表 ⑦ 印的「摘要正文上限」在这个预算下仍是 1500：10% 的派生值只有 800，被夹回下限。与调预算
  之前一模一样是预期，不是派生没生效；
- 逐轮观测里 `摘要` 从 0 变 1，同一轮 `消息数` 明显掉下来。**`≈字符` 不一定跟着掉**——快照是那轮跑完
  之后取的，压缩发生在轮首，新一轮自己加的字符会把降幅盖掉（实测 t04：消息数 10→9，字符 6595→6780
  反而涨了）。要看压缩本身的量只能看日志 `上下文压缩完成` 那行的 `总字符: A -> B`；
- `t_agent_context_compaction` 里该会话有三到四行（实测 4 行：素材 6/8/8/12 条，
  上下文 6648→3416、9598→3700、8300→3209、9043→4169，单次回收 55%~64%）；
- `判定` 里 `会话摘要资产已生成` 与 t09 / t14 两条中期召回都转成 PASS；
- **t09 / t14 未重查 search_knowledge** 是 PASS——摘要把结论带过来了，模型不必回头重查；
- **锚点在状态里始终可寻回** 仍然是 PASS——压缩会真删早期原文，锚点届时活在摘要里，两头都丢才是越界；
- **上下文里没有孤儿 tool_use / tool_result** 仍然是 PASS——压缩只在用户轮起点切，切点前后各自配得齐，
  出现孤儿会让 DeepSeek 直接返回 400。

### 让裁剪确定性地触发

裁剪是先动手的那层，摘要开不开都照跑，所以只要把预算调到实测峰值的两倍以内即可：

```yaml
agent:
  memory:
    context-window-chars: 8000  # 裁剪门落在 4000
    summary-enabled: false      # 可选：关掉压缩层，让这一跑只观测裁剪
```

「最小回收量 = 当前总量的 20%」是编译期常量，没有旋钮。越过门之后若报告里
`可回收量粗估` 那行的合计低于折算下限，日志会打 `上下文裁剪跳过, 可回收 … 下限 …`——这时要加的是
撑量轮（让 `search_knowledge` 多返回几块），不是继续往下调预算：预算调得越低，下限的绝对值跟着更低，
但受保护的最近两个循环占的比重会更高，反而更难够着。

重跑后应当看到 `已清理` 从 0 变成正数且只增不减，`工具结果裁剪已实际触发` 转 PASS，
`锚点原文始终留在上下文里` 仍是 PASS——裁剪只改写工具结果，从不删消息、也不碰用户说过的话。

**关掉 `summary-enabled` 之后 t09 / t14 仍然应当 PASS，别把它们的 FAIL 当成预期代价。** 这两轮问的
`B3-1207` 与 `NB-3160` 都出自**用户消息**（t02 / t10），而裁剪只改写 `tool_result`；压缩一关就没有任何东西
删得掉用户原话，模型是直接从原始历史里读到的。**这时候 FAIL 才是真信号**——说明有别的东西在吃用户文本。
真正会变的只有 `会话摘要资产已生成`：没有摘要消息，它转 **UNCOVERED**（不是 FAIL，退出码仍为 0）。

实测形态（08-25，8000 预算 / 15 轮）：**只在 t04 与 t06 各成功一次**（`14728 → 11177`，7 块；
`22048 → 16671`，4 块），随后 t07~t14 连续九轮全部空转。`已清理` 的轨迹是 `0 → 7 → 11` 然后平了。
原因见上文那张块类型表——不是回归，判定只要求 `已清理 > 0`，裁一次就够。

**顺带量到一个副产品**：裁剪只动了两次，前缀因此稳了九轮，`④ 命中缓存峰值` 达到 21248 token / 输入峰值
21587，命中率 98.4%。压缩每次都重写前缀，缓存代价比裁剪高得多——这是「回收的量值不值那次击穿」唯一的实测锚点。

验完记得把预算改回生产口径、把 `evictable-tools` 填回去。生产值该定多少不等于「换了哪个模型」：
先看那个模型的窗口，再把人设、工具 schema、本轮输出预留、字符折 token 的误差逐项扣掉，剩下的才是这个数。
不要照抄这里的调试值。

### 单会话排查

不想重跑对话、只想再看一眼某条会话的状态：

```bash
java -cp /tmp/ragent-regression-classes \
  com.nageoffer.ai.ragent.initializer.AgentMemoryProbeMain \
  --suite-dir resources/regression/agent-memory \
  --session <会话ID>
```

它只读 `t_agent_state`，不发起任何对话。会把该会话的消息数、四类内容块数量、每块 tool_result 的
体量、逐条 usage 全部摊开。锚点默认取剧本里的 `anchor`，用 `--anchor <关键词>` 可以查别的词——
拿它查线上会话「为什么忘了某件事」也是成立的。

### 改剧本

`turns.properties` 一行一个配置，加轮次只要在 `turn.refs` 里追一个 ref 再补上它的键：

| 键 | 含义 |
| --- | --- |
| `anchor` | 全场锚点，判定「记不记得」全靠它。**必须是知识库里查不到的内容**，否则模型检索一下就答出来了，验的就不是记忆 |
| `turn.<ref>.session` | `main` 复用主会话，`fresh` 另开新会话 |
| `turn.<ref>.tier` | `short-term` / `mid-term` / `long-term`，决定这轮是硬断言还是 PENDING |
| `turn.<ref>.text` | 真正发给 `/agent/v1/chat` 的问题 |
| `turn.<ref>.expect-any` | 回答里出现任意一个即算命中，`\|` 分隔；留空表示不判回答内容 |
| `turn.<ref>.expect-tool` | 期望调用到的工具。不命中记 UNCOVERED 而不是 FAIL——检不检索是模型自己的决定 |
| `turn.<ref>.forbid-tool` | 本轮不该调用的工具，调了即 FAIL。**「答案必须来自记忆」的轮次靠它判**：关键词问题里就带着，复述不算记住，重查一遍才是真没记住 |
| `turn.<ref>.purpose` | 报告里的说明文字 |

判定关键词只匹配正式回答，不匹配思考内容。模型「想到过」不算记得。

## 配置

`regression.properties` 里只有回归台自己的参数（账号、超时、重试）。服务地址、数据库账号和
`agent.memory` 三项开关全部从 `application.config` 指向的那份 `application.yaml` 读，回归台不另存
一份——报告里印的「配置阈值」必须和服务端正在用的是同一个值，否则整张校准表是假的。

例外是那几个派生比例：它们编译在 `AgentMemoryProperties` 里，yaml 中读不到，
`AgentMemoryRegressionMain` 顶上有一份手抄副本，**改了服务端那边这里必须同步**。

排查回归台自身报错时加环境变量 `RAGENT_REGRESSION_DEBUG=true`，会打印完整堆栈。
